# Развёртывание, обновление и восстановление

## Linux-сервер

Поддерживается Docker Compose v2. Сервер должен иметь доступ к Docker registry, npm/PyPI при сборке, публичным интерфейсам Steam при синхронизации и Telegram API при включённых уведомлениях. Закройте входящие порты, кроме 80/443 и необходимого административного SSH. Приложения не публикуют PostgreSQL/Redis/API непосредственно в production-конфигурации.

Первый запуск из корня репозитория:

```sh
./scripts/bootstrap.sh
```

Требуются Bash и Python 3 для генерации ключей. Скрипт не печатает пароль в журнал; прочитайте `ADMIN_PASSWORD` локально в `.env` и сохраните в менеджере секретов. Инициализация администратора выполняется при первом старте API. Изменение переменной после создания пользователя не является сменой существующего пароля. Не удаляйте `.env`: ключи и пароль БД нужны после перезапуска.

`postgres` и `redis` проходят healthcheck, API применяет миграции и проверяет БД/Redis через `/health/ready`, после него запускаются worker, inventory worker, scheduler и dashboard. Celery beat должен оставаться одним экземпляром. API/воркеры допускают масштабирование, но только после проверки блокировок и пределов БД в вашей нагрузке:

```sh
docker compose up -d --scale worker=3
```

## HTTPS

Для домена, указывающего на IP сервера, отредактируйте `.env`:

```dotenv
SITE_ADDRESS=farm.example.com
PUBLIC_ORIGIN=https://farm.example.com
TLS_EMAIL=operator@example.com
SESSION_SECURE=true
```

Порты 80/443 должны быть доступны для выпуска сертификата Caddy. Примените `docker compose up -d --force-recreate api worker inventory scheduler caddy`. `PUBLIC_ORIGIN` должен в точности соответствовать адресу браузера (схема, хост, порт). Сервер проверяет Origin и CSRF; неверный адрес может блокировать команды и WebSocket.

Для `localhost` Caddy выпускает сертификат внутренним CA. Получите **публичный корневой сертификат**:

```sh
mkdir -p artifacts
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt artifacts/caddy-root.crt
```

Доверьте этот сертификат в хранилище сертификатов своей ОС/браузера. На Windows устанавливайте только корневой сертификат вашего сервера, источник которого вы проверили. Приватный ключ CA не копируйте. У Windows Agent используйте настроенный доверенный CA в соответствии с его документацией, а для нескольких ПК предпочтителен настоящий домен. `https://localhost` на другом ПК относится к нему самому, поэтому агентам нужен доступный DNS-адрес сервера и соответствующий сертификат.

## Обновление

Сначала сделайте резервную копию БД и `.env` в защищённое место. Получите новую версию исходников, затем:

```sh
./scripts/backup.sh
docker compose build
docker compose up -d --wait
```

Миграции выполняются API при запуске. Проверяйте обратимость конкретной миграции перед откатом; восстановление старого образа поверх изменённой схемы не гарантируется. Никогда не запускайте две конкурирующие миграции вручную. Рабочие сессии необходимо корректно остановить перед обслуживанием узлов.

## Резервные копии

`./scripts/backup.sh` создаёт PostgreSQL custom-format dump в `backups/` с приватными правами. Он не включает `.env`, сертификаты Caddy и локальные credentials агентов: храните их отдельно, зашифрованно. Скрипт сначала пишет `.partial` и публикует файл только после успешного `pg_dump`. Настройте ежедневный cron/timer на хосте и перенос копий за пределы сервера. Ротация файлов резервных копий выполняется оператором.

Восстановление **заменяет существующие данные** и останавливает приложения. После создания дополнительной копии:

```sh
./scripts/restore.sh backups/farm-YYYYMMDDTHHMMSSZ.dump --replace-database
```

Скрипт проверяет формат, останавливает приложения, восстанавливает БД одной транзакцией и поднимает сервисы. При ошибке приложения остаются остановленными для диагностики. Не продолжайте запись в частично восстановленную систему. Проверяйте восстановление на изолированной установке, а не впервые во время аварии.

Обычный `docker compose down` сохраняет named volumes. `docker compose down -v` уничтожает БД, очередь и сертификаты; такая команда не используется ни установщиком, ни backup/restore скриптами.

## Диагностика

```sh
docker compose ps
docker compose logs --tail 150 api worker inventory scheduler
docker compose logs --tail 100 caddy
```

`/health` проверяет доступность процесса API, `/health/ready` — готовность зависимостей. Онлайн-статус узлов определяется heartbeat. Steam, Telegram и температура/GPU могут быть недоступны независимо от готовности БД.

Если Docker build в управляемом облачном окружении требует session CA, создайте временный Compose override с `build.secrets: [proxy_ca]` и top-level `secrets.proxy_ca.file` на доверенный системный bundle. Dockerfiles принимают необязательный BuildKit secret `proxy_ca` только на этапе загрузки зависимостей; сертификаты и ключи не попадают в image. Используйте штатные proxy-переменные среды и не отключайте проверку TLS.

## Масштабирование и ограничения

Раздельная очередь inventory ограничивает внешнюю нагрузку на Steam независимо от игровых заданий. Добавление воркеров не отменяет Steam rate limits. PostgreSQL должен иметь резерв диска и лимит соединений; телеметрия подлежит retention. Начните с одной реплики API/beat и измерьте ваш поток команд до масштабирования. Нагрузочный скрипт реестра не заменяет испытания на сотнях физических узлов.
