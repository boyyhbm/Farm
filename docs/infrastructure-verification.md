# Фактические проверки инфраструктуры

Проверено 2026-11-03 в Linux-окружении Python 3.12, Node.js 24, Docker 29.9.2. Результаты относятся к данному окружению и исходникам на момент запуска.

- `docker compose config --quiet` и объединение с `docker-compose.dev.yml` — успешно.
- `bash -n scripts/bootstrap.sh scripts/backup.sh scripts/restore.sh` — успешно.
- `python -m py_compile tests/load/accounts.py` — успешно.
- Настоящие PostgreSQL 17.11 и Redis 7 подняты в Docker и прошли healthcheck.
- `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile` в реальном контейнере Caddy — успешно.
- API Docker image собран с установкой зависимостей и включённой проверкой TLS. Последующие изменения приложения требуют повторной сборки.
- Полный Docker Compose не запущен: VFS в этом окружении копирует слои/файловую систему контейнеров, и общий диск 8 GB закончился при создании нескольких экземпляров API. Неиспользованные тестовые образы и build cache удалены; PostgreSQL/Redis сохранены. Ошибка не скрыта и не считается успешным полным развёртыванием.
- Реальный `./scripts/backup.sh` создал custom-format PostgreSQL dump, `pg_restore --list` прочитал его. Дополнительно выполнены `pg_dump`/`pg_restore` из `farm_load` в отдельную БД `farm_restore`; 5 000 записей сохранились. Разрушающий production-restore script целиком не запускался поверх основной БД.

## Нагрузка реестра

Проба использовала отдельную БД `farm_load`, Redis DB 1 и один локальный Uvicorn на порту 8001. Основная БД не заполнялась нагрузочными записями. Для каждого измерения реестр очищался **только в изолированной тестовой БД**. CSV содержит синтаксически валидные вымышленные SteamID и явную пометку теста; запросов к Steam не было.

| Записей в реестре | Импорт CSV | Успешные чтения | Параллельность | Время 200 чтений | Чтений/с | p95 |
|---|---:|---:|---:|---:|---:|---:|
| 1 000 | 1.038 s | 200/200 | 8 | 1.890 s | 105.79 | 118.19 ms |
| 5 000 | 5.773 s | 200/200 | 8 | 2.953 s | 67.72 | 183.82 ms |

Страница — 50 записей. Ошибок HTTP в этих двух пробах не было. Исходные измеренные поля и время запуска сохранены в [load-results.json](load-results.json); исполняемая проба — [tests/load/accounts.py](../tests/load/accounts.py). Между пробами очистили лимиты только изолированной Redis DB 1, чтобы второй замер не наследовал счётчик предыдущего. Лимит API не отключался.

Это измерения импорта и постраничного чтения реестра, а не длительный stress/soak test. Во время разработки окружение использовалось совместно со сборками и тестами. Результаты не доказывают производительность сотен агентов, Steam API, одновременных игровых процессов или production-устойчивость; для них нужны отдельные стенды и физические Windows-ПК.
