# Farm Protection & Risk Management (0.3.0)

Модуль работает в существующем Windows Manager и веб-панели: **Защита / Protection** в меню, карточка Protection на Dashboard и переход из Account Manager. Данные хранятся в основной SQLite/PostgreSQL, миграция `0003` сохраняет существующие записи.

## Настройка через интерфейс

1. Откройте **Защита → Настроить ключ** на главном компьютере и сохраните свой Steam Web API key. Ключ защищается Windows DPAPI в профиле пользователя Manager. Он не возвращается API и не сохраняется в таблицах или frontend bundle. Пустое поле отключает интеграцию. В серверной Linux-поставке ключ задаёт администратор развёртывания через secret `STEAM_API_KEY`.
2. Нажмите **Проверить сейчас**. Результаты появляются после выполнения фоновой задачи и реального ответа Steam. При отсутствии ключа сведения остаются неизвестными. Автоматическая проверка обходит активные аккаунты партиями до 100; интервал по умолчанию — 6 часов.
3. Для Steam/CS2 сначала вручную войдите в официальный Steam на нужном ПК, проверьте SteamID и нажмите **Вход** в строке аккаунта. Укажите ПК, срок, основание и явное подтверждение. Это заявление оператора, а не проверка авторизации через Steam API. Подтверждение другого аккаунта на том же ПК отменяет предыдущее.
4. При необходимости включите **Требовать свежую успешную проверку Steam API**. По умолчанию неизвестные сведения требуют проверки, но не объявляются блокировкой. Ручное подтверждение авторизации обязательно для Steam/CS2 независимо от этой настройки. Изолированный синтетический Test Engine работает отдельно.
5. Используйте **История**, ручную паузу, принятие и закрытие инцидентов. Закрытие инцидента не удаляет доказательства блокировки и не разрешает запрещённые действия. Все изменения проходят RBAC, CSRF и аудит.

## Источники и границы сведений

Источник блокировок: официальный [ISteamUser/GetPlayerBans](https://partner.steamgames.com/doc/webapi/ISteamUser#GetPlayerBans), HTTPS GET `https://api.steampowered.com/ISteamUser/GetPlayerBans/v1/`. Авторизация передаётся заголовком `x-webapi-key`, без ключа в URL. [Документация аутентификации Web API](https://partner.steamgames.com/doc/webapi_overview/auth) допускает этот заголовок. Документация сверена 4 ноября 2026 года.

| Сведение | Интерпретация |
| --- | --- |
| VACBanned | Полученное логическое значение; источник и последнее успешное время доступны в строке и истории. |
| CommunityBanned | Полученное логическое значение, без предположений. |
| NumberOfGameBans | Подтверждённое количество на аккаунте; не выдаётся за подтверждение конкретного CS2-бана. |
| EconomyBan | Только документированные `none`, `probation`, `banned`; неизвестное значение остаётся неизвестным. |
| Торговые ограничения | GetPlayerBans не предоставляет надёжного полного статуса; API возвращает `null`. Приватный инвентарь не объявляется торговым баном. |
| Вход в Steam | Ограниченное по времени подтверждение оператора на конкретном ПК с источником и временем. Не считывает пароли или Steam Guard. |
| Соединение агента | Наблюдение TLS на слушателе/доверенном proxy и время heartbeat. Неподтверждённый транспорт не показывается как защищённый. |

Успешная проверка — наблюдение в прошлом, а не гарантия текущего состояния. Ошибки сети, неверный ключ, HTTP 429, неполный или некорректный ответ не очищают ранее подтверждённые сведения. История хранит каждую попытку и источник. Модуль не прогнозирует VAC и не обещает предотвращать санкции Steam.

## Оценка и защитные действия

- **LOW**: в доступных свежих сведениях нет обнаруженных проблем и имеется действующее подтверждение входа.
- **MEDIUM**: неизвестные/устаревшие сведения, неподтверждённый вход, сбои интеграции или неподтверждённый транспорт.
- **HIGH**: ошибка входа, ручная пауза, потеря узла или существенный инцидент.
- **CRITICAL**: подтверждённое ограничение или аварийная остановка инфраструктуры. Обоснование всегда доступно.

Compliance Engine проверяет создание, повтор, назначение и исполнение Steam/CS2-заданий. Запрещены неизвестные операции, автоматическое получение XP/наград на официальных серверах и произвольные команды. Подтверждённое ограничение, ошибка входа, истёкшее/несовместимое подтверждение либо ручная пауза отменяют затронутые задания и сохраняют команды безопасной остановки. Очередь синтетических тестов остаётся независимой.

Частичный уникальный индекс БД запрещает две активные сессии одного аккаунта. Сессии `UNKNOWN` продолжают резервировать аккаунт/узел до сверки процессов: отсутствие связи не считается успешной остановкой. Аварийная остановка останавливает управляемые сессии и приостанавливает очередь; офлайн-команды дожидаются восстановления связи.

HTTP 429 устанавливает общий cooldown для инвентаризации и Protection. Глобальная lease исключает параллельные проверочные партии. HTTP 401/403 приостанавливает интеграцию до исправления ключа и явного повтора; это не ошибка авторизации Steam-аккаунта. Повторные попытки ограничены. Проверка API не удерживает SQLite writer lock во время сети.

Инцидент содержит код, уровень, привязанные сущности, источник, время, диагностические сведения без секретов и рекомендацию. Событие попадает в аудит и существующую очередь Telegram-уведомлений, учитывающую настройки и уровень важности. Без настроенного Telegram отправка не заявляется выполненной. Открытые инциденты дедуплицируются. История проверок и закрытые инциденты старше 365 дней очищаются существующим retention worker; текущие подтверждённые ограничения сохраняются.

## Обновление и проверки

Перед обновлением используйте **System Management → Резервная копия**. Миграция не удаляет аккаунты и настройки. Если старая база уже содержит конфликтующие активные сессии одного аккаунта, создание защитного индекса завершится диагностической ошибкой; данные не удаляются автоматически. Разрешите конфликт через существующий Session Manager перед повторным обновлением.

Автотесты используют явно заданный `httpx.MockTransport` только в тестах: подтверждённый бан, неизвестные сведения, неправильные типы/SteamID, недоступный API, 429, неверный API-ключ, авторизация, ручная пауза, очистка секретов, lease, потеря узла, аварийная остановка, RBAC, 24 узла/48 заданий и реестр 1200 аккаунтов. Это проверка логики, а не результат обращения к реальным Steam-аккаунтам. Production mock-режима нет.

Windows CI проверяет новые тесты, миграцию базы `0002 → 0003`, упаковку Protection API/страницы, установку, автоматический запуск backend, persistence, две настоящие SCM-службы агентов и удаление. Фактический результат конкретного запуска указывается отдельно в отчёте поставки; документ не объявляет ещё не выполненные проверки успешными.
