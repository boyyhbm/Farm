# Farm Protection Engine 2.0 — приложение 0.4.0

Это расширение существующего Protection, Account Manager, Node Manager и планировщика. Установка и работа остаются графическими: используйте Manager/Agent Setup EXE. Python, Node.js, Docker и ручное редактирование файлов пользователю Windows не требуются.

## Что работает постоянно

Safety Engine выполняет цикл каждые 5 секунд независимо от сетевой проверки Steam. Desktop использует отдельный поток; PostgreSQL/Redis-развёртывание — отдельный Celery worker и очередь `safety`. Планировщик также проверяет безопасность перед назначением заданий. Последний успешный цикл сохраняется в БД; интерфейс показывает устаревший heartbeat сервиса вместо ложного RUNNING.

Локальный guard агента работает при потере WSS-соединения. Он проверяет доступные ресурсы, сохраняет блокировку на диске и останавливает исключительно процессы, которыми владеет Farm Agent. Отсутствие связи не считается завершением задания. Другие узлы продолжают разрешённую работу.

## Account Health и достоверность

Статусы **Healthy, Warning, Restricted, Banned, Unknown** вычисляются по наблюдениям Steam, ручному подтверждению входа, инвентарю, привязанному узлу и открытым инцидентам. Каждое наблюдение имеет объяснение, источник и время. Время вычисления Health не подменяет время получения сведений Steam.

Подтверждённые VAC/Community/Game ban сведения поступают из официального GetPlayerBans; количество game bans не выдаётся за доказательство CS2-бана. Economy ban учитывается при документированном значении. Полный достоверный торговый статус не предоставляется этим интерфейсом и остаётся неизвестным. Авторизация — ограниченное по времени подтверждение оператора на конкретном ПК. Пароли Steam/Steam Guard не собираются. API-ключ в Windows защищён DPAPI.

Недоступность API, неверный ключ, 429 и приватный инвентарь не превращаются в выдуманный бан. Сохраняются предыдущие сведения, источники и история. Используются существующие пакетные проверки до 100 аккаунтов, общий cooldown, lease и ограниченные повторы. Модуль не прогнозирует VAC и не получает сведения о скрытых проверках Valve.

## Решения и условия возврата

| Событие | Защитное действие | Возврат |
| --- | --- | --- |
| Подтверждённый бан / economy restriction | Запрет Steam/CS2, отмена затронутых заданий и управляемая остановка | Только достоверное новое наблюдение и разрешённая операция; закрытие инцидента не очищает факт |
| Ошибка / истечение подтверждения входа | Остановка затронутых Steam/CS2-заданий | Ручной вход в официальный клиент и новое подтверждение SteamID/узла |
| Steam 429 | Общий cooldown для Steam-запросов | После Retry-After; без обхода лимитов |
| Web API 401/403 | Приостановка интеграции; не объявляется выходом Steam-аккаунта | Исправление ключа и явное разрешение повторной проверки |
| Сеть / отключение узла | UNKNOWN и сохранение резервирования сессии | Переподключение, сверка процессов и подтверждённых результатов |
| Перегрев / критическая RAM / нехватка диска | Локальная остановка и REVIEW_REQUIRED только затронутого узла | Исправление, свежие проверки, администратор и ACK локального guard |
| Устойчивая высокая CPU | После заданного периода — REVIEW_REQUIRED | Проверка причин и ручной возврат после нормализации |
| Изменение собственных компонентов / игровых EXE/DLL | REVIEW_REQUIRED, остановка управляемых операций | Ремонт официальной поставкой; для игровых файлов — проверка в Steam и новый подтверждённый эталон |
| Три сбоя Steam/CS2-сеансов аккаунта за 15 минут | Ручная пауза только этого аккаунта | Проверка ошибок и явное снятие паузы; не бесконечный перезапуск |
| Просроченная / неудачная остановка | Новая ограниченная попытка без освобождения сессии; после трёх автоматических попыток — REVIEW_REQUIRED | Проверка процессов и явная остановка/перезапуск службы через GUI |
| Повреждение локального состояния guard | Блокировка, без молчаливого сброса | Проверка и явный возврат после успешных локальных проверок |
| Неуспешное обновление | Сохранение диагностики/отката и блокировка по найденному сбою | Ремонт установщиком, «Ремонт проверен», новая проверка и отдельный возврат узла |
| Повреждение Manager | Пауза очереди и остановка управляемых заданий; cached failure нельзя обойти Resume | Ремонт, «Проверить Manager», затем явное возобновление |

Решения сохраняются в `safety_decisions` и Audit Log. Инциденты поступают в существующий Telegram-outbox с настройками важности и повторов. Секреты исключаются из диагностических данных. История и закрытые события имеют retention; текущие блокировки и последняя проверка узла сохраняются.

## Графический процесс проверки узла

1. Откройте **Защита → Distributed node safety**. При необходимости нажмите **На проверку**: остановки и локальная блокировка отправляются этому узлу.
2. Исправьте причину. Настройте реальные пути Steam/CS2 через графические настройки агента. Удалённая игра не должна лишать агент возможности передавать телеметрию.
3. Нажмите **Проверить** и дождитесь фактического результата агента. Команда в очереди не объявляется успешной проверкой.
4. Для игрового эталона сначала выполните официальную проверку файлов в клиенте Steam. Остановите управляемые процессы и нажмите **Эталон**, явно подтвердив проверку. Эталон сравнивает выбранные EXE/DLL Steam и двух стандартных каталогов CS2; VPK и все возможные модификации этим не покрываются.
5. Нажмите **Разрешить работу**. Состояние будет RELEASING до ACK агента, который повторит локальные проверки. При отказе локального guard узел останется на проверке. Отменённые задания, ручные паузы аккаунтов и подтверждения Steam не восстанавливаются автоматически.

Viewer читает данные и отчёты. Operator может запрашивать проверку целостности. Политику, эталон, ручную блокировку, ремонт и возврат меняет администратор с явным подтверждением. Политика и решения доступны через GUI; терминал не нужен.

## Целостность и датчики

Установщик поставляет SHA-256-эталон runtime, Python-компонентов, а у Manager — `app.asar`, Node.js и собранных ресурсов Dashboard. При наличии подписывания хеши обновляются после Authenticode. Агент проверяет собственные файлы, доступные подписи исполняемых компонентов и выбранный игровой эталон. Проверка повторяется примерно каждые 5 минут; её можно запросить вручную.

**Совпадение с локальным неподписанным эталоном не доказывает подлинность издателя.** Интерфейс отдельно показывает `unsigned_local_manifest` и фактический Authenticode-статус. Поставки без эталона показывают Unknown. Изменения памяти, DLL injection, скрытие процессов, обход VAC, подмена идентификаторов и сетевая маскировка отсутствуют.

CPU-температура доступна через поддерживаемые OS sensors или уже установленный WMI provider Libre/OpenHardwareMonitor; GPU-температура — через доступный официальный `nvidia-smi`. Драйверы не устанавливаются и не загружаются. Без датчика отображается Unknown. Нельзя гарантировать температурную защиту по отсутствующим показаниям.

Начальные критические пределы локального guard: CPU 95 °C, GPU 90 °C, RAM 97%, свободная RAM менее 0.5 GiB или диск менее 0.5 GiB. Центральные пороги настраиваются в Safety Policy. Более мягкая серверная настройка не отключает локальные защитные пределы. Неизвестные и устаревшие показания не выдаются за актуальные измерения; некорректные числа и NaN отклоняются.

## Данные и эксплуатация

Миграция `0004` добавляет пять таблиц, а `0005` сохраняет явную ссылку на последнюю проверку Manager без зависимости от точности часов Windows без удаления прежних данных. Перед обновлением используйте System Management → Backup. Сохраняются SQLite Desktop и PostgreSQL/Redis/Celery Server. Разрешённые тестовые задания не требуют Steam-аккаунтов и не взаимодействуют с официальными матчами.

Вкладка Protection предоставляет поиск, фильтры, историю Health/инцидентов/целостности/решений, CSV и JSON. CSV защищён от формул из пользовательских полей. Source/observed timestamps доступны в отчётах. Экспорт истории ограничен 50 000 записями за запрос; реестр аккаунтов экспортируется полностью.

SCM восстанавливает агент после сбоя с двумя ограниченными попытками (5 и 15 секунд), затем оставляет его для диагностики. Фактическую перезагрузку Windows и работу на нескольких физических ПК необходимо проверять отдельно от рестарта службы в CI. Прошедшие проверки перечисляются в отчёте конкретной сборки; документ не объявляет ещё не выполненный Windows-прогон успешным.
